# Native scatter backward at tied and empty graph segments

This [small probe](../../bench/probe_scatter_backward_mps.py) separates two
questions that a future segmented reduction kernel must not conflate:

1. What gradient follows from a mathematical reduction over **source edges**?
2. What gradient does the pinned native PyTorch operation actually return?

The [Safe](../../bench/results/2026-10-01-apple-m5-pro-scatter-backward-safe.json)
and [Fast](../../bench/results/2026-10-01-apple-m5-pro-scatter-backward-fast.json)
raw JSON files retain the source/index/upstream tensors, independent Python
oracle, CPU and MPS outputs and source gradients, and 20-repeat stability
checks. The matching [Safe](../../bench/results/2026-10-01-apple-m5-pro-scatter-backward-safe.md)
and [Fast](../../bench/results/2026-10-01-apple-m5-pro-scatter-backward-fast.md)
tables are generated by the script. Both modes used M5 Pro, macOS 26.5.2,
PyTorch 2.14.1, float32 values, int64 indices, and
`PYTORCH_ENABLE_MPS_FALLBACK=0` before importing PyTorch. The script SHA-256
in both JSON files is
`5bbea5d67a246ac25217ca0ff3105311dd249358efa780d615ad09e6ff31c37f`;
the repository base at capture was
`94398da77fb305039c9648380182d55747609ad1`.

## Fixture and observations

Six two-channel source edges map to output nodes `[0, 0, 0, 2, 2, 2]`.
Nodes 1 and 3 have no edges but receive nonzero upstream gradients. In every
operation, their forward values are zero and they contribute no source-edge
gradient. The probe invokes native `scatter_add_` and
`scatter_reduce_(include_self=False)` with `sum`, `mean`, `amax`, and `amin`.

All five forward outputs and all five MPS source gradients matched native CPU
in Safe and Fast Math. Each observed output and gradient was bitwise stable
over 20 repeats **for this exact fixture**. `scatter_add_`, `sum`, and `mean`
also matched the independently derived source gradient.

The exact-zero extreme gives a counterexample for a blanket native-parity
claim about max/min backward:

| Case | Source values in node 2 | Upstream gradient | Mathematical source-edge gradient | Native CPU and MPS source-edge gradient |
| --- | --- | ---: | ---: | ---: |
| `amax`, channel 1 | `[-1, -1, 0]` | `4` | `4` for the edge with value 0 | `2` |
| `amin`, channel 0 | `[4, 4, 0]` | `3` | `3` for the edge with value 0 | `1.5` |

The forward extrema are correctly zero. At nonzero exact ties, native CPU and
MPS split the gradient among the tied source edges as the mathematical
oracle does. The halved zero-extreme gradients are **observations** of
PyTorch 2.14.1, not evidence of a particular implementation cause. Counting
the initial output zero as an additional tie would produce the observed
halves, but that is only an inference; the probe does not inspect PyTorch's
backward implementation.

For a future kernel, the **mathematical contract** may split gradient among
source extrema only. A **native PyTorch parity contract** must account for
this zero-extreme case or explicitly declare a difference. The project should
choose and test the public contract before implementing the kernel. This
probe does not specify `torch_scatter` arg-index sentinels, NaN/Inf handling,
other dtypes, or universal bitwise determinism, and it contains no timing.
PyTorch's [`include_self=False` definition](https://docs.pytorch.org/docs/2.14/generated/torch.Tensor.scatter_reduce_.html)
is the forward-operation reference; the backward discrepancy above is an
empirical result for the pinned release.
